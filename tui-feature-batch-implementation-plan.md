# TUI feature batch — implementation plan

## Context

The user filed ~30 UI/UX requests against `src/tui` (a mature `@opentui/react` app: `App` in `app.tsx` holds ~20 `useState`s and wires `Sidebar`, `Timeline`, `Composer`, `DiffPanel`, `TasksPanel`, `PickerModal`). Three research passes (protocol/server audit, OpenTUI capability audit, model-layer audit) established what's actually buildable:

- **Fully client-side buildable** (~24 of 30 items): layout, hover, modal chrome, toasts, scroll regions, timestamps, provider colors, selection/clipboard, external editor, diff-turn picker, composer bugs.
- **Blocked on missing server/protocol support** — confirmed via full grep of `src/threads/threadApi.ts`, `src/types.ts`, `src/cli.ts`, `src/handover/`: **revert/rollback a turn, fork a thread, archive, rename/regenerate-title, mark-unread, compact-session, list-skills, token/context-window size, cache-hit status**. None of these commands or fields exist anywhere on the wire today (`thread.delete` exists only as an internal recovery command in `handover.ts:243`, never general-purpose). These are called out per-item below as **deferred** — I will not fake functionality for them; where the user asked for UI (Message Actions modal, Command Palette) I'll build the shell with working items live and blocked items visibly disabled, not silently missing, so the affordance is discoverable once server support lands.

Given the size, this lands as several sequential stages (separate sittings), each verified with the existing `bun src/tui/render-check.tsx` snapshot harness (mocks a `TuiClient`, scripts mouse/keyboard, captures char frames — no live terminal needed) before moving to the next stage.

## Stage 0 — Shared foundations

New file `src/tui/hooks/` directory for the runtime-hook decomposition (borrowed from gloomberb's pattern: `app.tsx` should shrink toward wiring, not grow — every new stateful concern below goes into its own hook instead of another inline `useState` block):

- **`useHover()`** (`src/tui/hooks/useHover.ts`) — OpenTUI has no built-in hover state (confirmed: only private `recheckHoverState()` internals); wraps the `onMouseOver`/`onMouseOut` + `useState` pattern already duplicated in `sidebar.tsx`'s `ModePillButton`/`NewThreadButton`. Returns `{ hovered, handlers: { onMouseOver, onMouseOut } }`. Retrofit `ModePillButton`/`NewThreadButton` to use it, then reuse everywhere in Stage 2.
- **`useToasts()`** (`src/tui/hooks/useToasts.ts`) — replaces the ad hoc `notices` array + three separate timeout effects in `app.tsx` (quit-armed `:157-161`, error `:165-169`, usage-limit has no timeout today). API: `push(tone, text, ms?)`, `dismiss(id)`, returns `toasts: {id, tone, text, createdAt, ms}[]`. Existing quit/error/usage-limit notices become `push(...)` calls; add manual dismiss (x) alongside auto-expiry.
- **`ModalShell`** (`src/tui/modalshell.tsx`) — shared chrome for every modal added below (PickerModal already exists; Message Actions, Command Palette, Diff-turn picker, Ctrl+C confirm all need the same chrome). Backdrop: full-screen `<box position="absolute">` with `backgroundColor` dark + `opacity: 0.5` (confirmed: every `Renderable` has an `opacity?: number` prop — `node_modules/@opentui/core/Renderable.d.ts:71`) instead of today's fully-transparent click-catcher. Panel: `borderStyle="single"` (not `"rounded"` — confirmed valid value alongside `"double"`/`"heavy"` in `node_modules/@opentui/core/lib/border.d.ts:15`). Refactor `PickerModal` to render inside `ModalShell` instead of owning backdrop/border directly.
- **Clipboard util** (`src/tui/model/clipboard.ts`) — thin wrapper over `createClipboard({ host, terminal })` from `@opentui/core` (`lib/clipboard.d.ts:51-126`), called with `destination: "all-available"` so a single `copyText(text)` call attempts both host-OS clipboard *and* OSC 52 (the SSH-safe path — `CliRenderer.copyToClipboardOSC52`/`isOsc52Supported`, `renderer.d.ts:563-565`) in one shot. This satisfies the "OSC 52 support" ask directly; I'm treating "5522" in the request as a typo for 52 — there is no such second OSC code, so only 52 is implemented. Every new copy feature below (text selection, copy button, message actions, command palette) calls through this one util, and pushes a toast via `useToasts`.
- **`clockTime(value, now)` rewrite** (`src/tui/model/turns.ts:119-124`) — add same-day/same-week/older formatting (hour-only / `Weekday, HH:MM` / `DD Mon, HH:MM`), using `now` for the comparison. Thread the `now` prop into `PromptBlock`, `ReplyBlock`, `ActivityRow` in `timeline.tsx` (currently only `WorkFold`/`TurnBlock` receive it — confirmed by the model-layer audit).
- **Provider color map** (`src/tui/theme.ts`) — new `PROVIDER_COLOR: Record<string, string>` keyed by substring match on `ProviderSummary.driver`/`instanceId` (`src/catalog/catalog.ts:42-53` has no brand-color field, confirmed — this has to be a client-side guess, same pattern as `sidebar.ts`'s hashed `BADGE_COLORS`). Best-effort hexes: Claude `#DE7356`, Codex/OpenAI `#74AA9C`, OpenCode `#8B5CF6` — cosmetic, easy to retune after a visual check.

## Stage 1 — Layout & modal/toast visual pass

- **Sidebar width + "+" placement** (`app.tsx:66` `SIDEBAR_WIDTH`, `sidebar.tsx:210-238`): bump width (38 → ~44). Replace the absolutely-positioned floating `NewThreadButton` (`sidebar.tsx:222-224`) with a normal flow element: put the mode-pill row in `justifyContent: "space-between"` with the pills wrapped in one flex-centered box and the "+" button as a trailing sibling — no more absolute overlap.
- **Modal corner/dim treatment**: apply `ModalShell` from Stage 0 to `PickerModal` (`pickermodal.tsx`), replacing its own `borderStyle="rounded"` backdrop (`pickermodal.tsx:132-149`) and the transparent backdrop box in `app.tsx:1041-1047`.
- **Toast redesign** (`app.tsx:1018-1040`): rebuild on `useToasts`. Match `Composer`'s padding convention (`paddingLeft/Right: 2, paddingTop/Bottom: 1` from `composer.tsx:136-140`), add an "x" dismiss glyph (mouse-down callback into `dismiss(id)`), and constrain position/width to the Timeline pane's own box bounds (compute left/width from `SIDEBAR_WIDTH + CHAT_GUTTER` and `chatWidth`, the same geometry `app.tsx` already computes at `:780-783`) with a 1-col inset, instead of the current screen-relative `right: 1`.
- **Settled-list scroll region** (`sidebar.tsx:309-333`, `model/sidebar.ts:156-210`): wrap `sections.settled.map(...)` in its own `<scrollbox>` with a fixed max height (~10 rows) instead of the current plain `flexShrink:0` box with no scroll region (confirmed — today only the *active* list has a `<scrollbox>`, settled has none). Keep the existing `settledLimit`/`SETTLED_PAGE`/"+N more" pagination underneath it.
- **Scrollbar focus color** (`timeline.tsx:763-767`, and add to `diffpanel.tsx`'s scrollbox / sidebar's active-list scrollbox): make `verticalScrollbarOptions.trackOptions.foregroundColor` (thumb) conditional on the pane's `focused` boolean — confirmed live-swappable per render, same mechanism as the existing `borderColor={focused ? ... : ...}` pattern. Unfocused: `COLOR.dim`/greyish; focused: `COLOR.accent`.
- **Work-fold expand direction / "peek" fix** (`timeline.tsx:597-668`): confirmed the reported bug is real, just not where initially suspected — `stackWorkEntries`/`ToolStack`'s `entries.slice(-1)` already correctly picks the latest entry of *a* stack; the actual all-or-nothing point is `TurnBlock`'s outer gate (`timeline.tsx:604`: `workExpanded ? (...) : null`), which hides *every* work block, not just older ones, once a turn is finished and folded. Fix: when folded (`workExpanded === false`), still render a one-row "peek" of the single most-recent work block (its `ToolStack`/single representative row) — matching the always-visible behavior while `open` — so only *earlier* blocks disappear behind the fold, not the latest one. This also happens to answer the "expand downward not upward" ask: work entries already render strictly *below* the `WorkFold` toggle and *above* the reply (confirmed via JSX order `:599-666`) — expanding is already additive-downward; no change needed there, it was likely the peek-disappearing bug being misread as a scroll-direction bug.
- **Diff panel label**: `diffpanel.tsx:145` ` diff ` / ` diff turn ${turnCount} ` → capitalize to `Diff`.

## Stage 2 — Hover + selection/clipboard sweep

- **Hover pass**: apply `useHover()` to every clickable element that currently lacks visual feedback: composer's model/effort/stop segments (`composer.tsx:172-190`), sidebar `ActiveCard`/`SettledRow` (`sidebar.tsx:23-107`), `DiffPanel`'s `FileSection` header row (`diffpanel.tsx:75-89`), `PickerModal` rows (currently highlight only follows keyboard `index` — add `onMouseOver` to also move `index` to the hovered row, mirroring termcn's dropdown pattern), `TurnDiffRow`/`WorkFold`/`ToolStack` toggle rows in `timeline.tsx`.
- **Text selection → clipboard + toast**: use OpenTUI's real selection system (`Selection`/`useSelectionHandler`, confirmed in `@opentui/react/src/hooks/use-selection.d.ts:12`) at the `App` root — on selection-end, read `renderer.getSelectedText()`, and if non-empty, call the Stage-0 clipboard util and `toasts.push("info", "Copied to clipboard")`.
- **Click-vs-selection conflict fix**: confirmed OpenTUI's selection model is a real reimplementation (not "let the terminal handle it") gated per-renderable by `selectable` (default true). Sweep every interactive chrome element (buttons, row backgrounds, borders, headers, pills) to `selectable={false}`, leaving `selectable` at its default (true) only on actual readable text — message/markdown bodies, diff content, command output — so a click-drag over a button no longer starts a text selection, and a drag over message text still can.
- **"Jump to bottom" toast**: confirmed net-new (no existing code or OpenTUI built-in — the reference image is from Claude Code, not this app). Track "is the chat pane scrolled away from bottom" using `ScrollBoxRenderable`'s `scrollTop`/`scrollHeight`/`viewport.height` (already used for `scrollPane` in `app.tsx:56-64`); when true, show a themed toast (via `useToasts`, non-auto-dismissing while the condition holds) reading `Jump to bottom (↓)` — no "ctrl+End" text — whose click scrolls `chatScrollRef` to bottom.

## Stage 3 — Composer fixes & additions

- **Model/effort picker broken in "creating" view** (`app.tsx:912-956`): two real bugs found. (1) `openModelPicker`/`openEffortPicker` (`app.tsx:676-699`) both start with `if (creating) return;`, which is the direct cause — remove that guard. (2) Once open, picking a model during `creating` must **not** dispatch `thread.model-selection.set` against the still-open *source* thread (`setThreadModel` targets `openThreadId`, `app.tsx:701-718`) — that would silently change the old thread's model instead of the new thread's. Add local `creatingModelSelection` override state, seeded from `selected.modelSelection`; branch `pickModel`/`pickEffort` on `creating` to update that local state instead of dispatching; `createThread` (`app.tsx:432-492`) uses `creatingModelSelection ?? source.modelSelection`. Then pass `onModelClick`/`onEffortClick` into the creating-view `<Composer>` (`app.tsx:936-952`, currently omitted) — this is the "reuse the composer, don't build two things" fix, since the component is already shared, it was just wired incompletely.
- **Copy-prompt button**: add a small "copy" segment next to the stop button in `composer.tsx`'s footer row (`:163-191`), calling the Stage-0 clipboard util on the current draft text + a toast.
- **Edit-in-external-editor**: new keybind in `Composer`/`App` — Alt+E everywhere, plus Ctrl+O as the Mac-reliable chord (macOS terminals don't send Option-as-Meta by default, so Option+E types ´; Ctrl+O arrives everywhere and is free in the textarea's bindings, firing App-level from the composer too — proven in-harness). No OpenTUI helper exists for this (confirmed) — implement via `renderer.suspend()` before spawn and `renderer.resume()` after (`CliRenderer.suspend/resume`, `renderer.d.ts:588-589`), spawning the preferred editor — explicit `$VISUAL`/`$EDITOR` first, otherwise the first available graphical default (VS Code, Zed, TextEdit via `open -W` on macOS; Notepad on Windows; `vi` elsewhere) — against a temp file seeded with the draft, `stdio: "inherit"` (new variant of the existing `runProcess` pattern in `src/infra/process.ts:22-75`, which today only pipes stdio). While the editor is open, the composer must reject input — track an `editingExternally` boolean and gate the `useKeyboard`/textarea. On editor exit, read the temp file back into the draft.

## Stage 4 — Diff-turn picker + timeline jump

- **Clickable "Diff turn N" header**: confirmed a `<box title="...">` is a decorative border caption with no click support (`Box.d.ts` has `titleAlignment`/`bottomTitle`, no `onTitleClick`). Replace `DiffPanel`'s border `title` prop with a custom header row above the scrollbox (mirroring how `Sidebar` already builds its own header rows), styled to read the same, with `onMouseDown` opening a new turn-picker modal (built on `ModalShell`, listing every `ThreadState.checkpoints` entry with `files.length > 0` — confirmed multiple coexist, `model/thread.ts:39`, `:187-194` — not just the latest).
- **Scroll timeline to the picked turn**: `groupTurns(entries)` already maps a checkpoint to its owning `TurnGroup` by `turnId` (confirmed, `turns.ts:75-77`, same lookup `TurnDiffRow`'s `expanded` check already does). Attach a ref per rendered `TurnBlock` (a `Map<groupId, RefObject>`), and on pick, compute that block's position and call `chatScrollRef.current.scrollTo(...)`. Flagging this as best-effort — exact scroll-into-view depends on confirming `TurnBlock`'s rendered `y` offset is reachable at implementation time; if not directly available, fall back to an approximate scroll (index / total-groups × scrollHeight).
- **Remove the `d` keybinding** (`app.tsx:557-561`) entirely, per the request — diff is opened only via the new clickable header now.

## Stage 5 — Command palette (new)

New `CommandPalette` modal (built on `ModalShell`, filterable list like `PickerModal`) with the requested actions. A protocol re-audit against `upstream/` (contracts + app + live 0.0.43-nightly server, protocol v1) overturned the original "deferred" calls — the V1 `DispatchableClientOrchestrationCommand` union (`upstream/packages/contracts/src/orchestration.ts:883-912`) already carries what we need:

| Action | Status |
|---|---|
| Copy project path / branch / thread ID / last assistant message | **Live** — all fields already in `shell`/`threadState`/`timeline()` |
| Jump to message (timeline) | **Live** — resolve to a `TurnGroup` index, reuse the Stage-4 scroll mechanism |
| Regenerate thread title | **Live** — `thread.meta.update` + `regenerateTitle: true` (V1 name is `meta`, not `metadata`); server advertises `threadTitleRegeneration` |
| Rename thread | **Live** — `thread.meta.update` + `title`, via a small `RenameModal` prompt (prefilled, 80-char cap) |
| Mark thread unread | **Dropped entirely** — `thread.mark-unread` is V2-only; our protocol-v1 server lacks it and the capability flag (`threadVisitedTracking`). The desktop menu item falls back to a browser-local mark on such servers, which a stateless CLI cannot meaningfully mirror |
| Archive thread | **Live** — `thread.archive`; moves selection to a fallback thread like delete, refuses the last visible thread (no unarchive path here) and refuses while drafting |
| Settle / unsettle thread | **Live** — `thread.settle` / `thread.unsettle` (+ `reason: "user"`); settled threads stay visible in the sidebar, so selection never moves |
| Delete thread | **Attempt, flagged risky** — `{type:"thread.delete"}` exists on the wire (`handover.ts:243`) but has only ever been dispatched as create-rollback; wiring it as a general action needs a live confirmation the server accepts it outside that flow (test against a real thread before trusting it in the UI — if it errors, fall back to disabled like the others) |
| Compact session | **Live** — no dedicated command exists, but the server interprets a normal turn with `text: "/compact"` and zero attachments (`RunExecutionService.ts:1293-1307`); provider support and empty threads surface as toastable server errors (empty threads render the row disabled up front) |

## Stage 6 — Message Actions modal (click a user turn)

New modal (on `ModalShell`, matches the screenshot: title + esc, search box, list) triggered by `onMouseUp` on `PromptBlock` (`timeline.tsx`) rows — up, not down, plus a live-selection check, so a text-selection drag ending on the prompt never opens it. The assistant's closing `ReplyBlock` opens the same modal (copy + revert resolve through its own entry/turn); superseded intermediate replies stay display-only. Both cards hover-brighten their border + speaker label (background untouched, so interiors never seam) to signal clickability. The modal is content-sized (`messageGeometry`, not the full picker frame). Rows: **Copy** (live, via Stage-0 clipboard, closes with a toast), **Revert** (live after all — see below). **Fork is intentionally omitted** — `thread.fork` is V2-only, so no UI for it at all rather than a disabled stub.

Revert audit correction: the V1 union *does* carry `thread.checkpoint.revert` / `thread.conversation.revert` (`{commandId, threadId, turnCount, createdAt}`), but no desktop UI triggers them. Wired as history-only `thread.conversation.revert` to `checkpointTurnCount - 1` (the file-restoring variant is never dispatched from here): two-step arm-confirm like delete, refused while a turn runs, followed by a subscription resync (our projector can't consume the removal event) and a diff-panel reset (it may show a deleted turn). Revert is offered on both user prompts and the assistant's closing reply — same turn, same target either way (a true fork/branch would need protocol-v2 `thread.fork`, which only truncates here). A missing checkpoint disables with a truthful reason: "turn still running" for the latest turn of a live session, "no checkpoint for this turn" otherwise. Toasts render above modals (`zIndex` 35) so errors fired from inside one stay visible. Backdrop-dismiss swallows the gesture's mouse-up for 250ms so dismissing onto a turn doesn't instantly act on it.

## Deferred — no server/protocol support exists today (not implemented this pass)

- Context-window usage (%, tokens, max) and cache-hit status: zero fields on the wire (`types.ts`, `threadApi.ts` both grepped clean for `cache|token|context|usage` beyond the unrelated provider-quota `ProviderUsageWindow`). Needs new server-side data before any UI is meaningful.
- Skills listing/picker: only a read-after-the-fact "skill" activity kind exists (`model/activity.ts:72-76`); no catalog/listing RPC to build a picker against.
- Revert (now live per Stage 6), fork (V2-only): fork stays omitted; mark-unread needs a protocol-v2 server advertising `threadVisitedTracking`.
- Answering agent questions in the TUI: LIVE (Stage 7) — the blocked verdict was wrong; the data was in `user-input.requested` activities all along. Approvals (`thread.approval.respond`) and attachments in answers remain out of scope.

These are flagged, not silently dropped — once the server exposes the missing commands/fields, the UI slots (Command Palette rows, Message Actions modal, a token/cache readout near the composer footer) are already designed to receive them.

## Stage 7 — Answer agent questions in the TUI

`pendingUserInputRequests` model (requested minus resolved by `requestId`, + tests) feeds an inline answer panel (`answerpanel.tsx`) replacing the composer while a request is live, Claude-Code style: question + options with descriptions, 1-9 quick-pick, toggle + Continue for multi-select, custom answer via the generalized rename prompt, sequential pages for multi-question requests, `thread.user-input.respond` on submit (confirmed live against the real server — needs `createdAt`; `runtime-request.respond` is V2-only and always 400s here), esc dismisses via `thread.user-input.dismiss` (also needs `createdAt`), and seen/settled sets so resyncs never reopen. Rejections re-check pending state after 800ms so answering elsewhere degrades to "Already answered elsewhere". The app swallows its own keys while the panel shows, exactly like a modal. Harness injects requests mid-run via a stashed emitter and covers submit + dismiss. Shipped alongside: a "waiting for input" `?` sidebar badge from the shell pending flags.

## Verification

After each stage: run `bun src/tui/render-check.tsx` (extend its scripted mouse/keyboard sequence to also exercise the new modals/toasts/hover states) and inspect the captured char frames + background-color histogram for regressions, plus `bun run typecheck` and `bun run test` (existing `model/*.test.ts` suite covers the pure-logic layer — extend it for the new `clockTime`, `useToasts`, and command-palette action availability logic). No live terminal session is required for this loop; a manual `t3code tui` smoke pass is worth doing once at the end for the mouse/selection/hover/external-editor pieces specifically, since those depend on real terminal mouse-reporting and process suspension that the snapshot harness can't exercise.
